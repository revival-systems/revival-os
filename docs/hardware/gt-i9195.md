**Researched:** 2026-11-08, from public sources only. **Nothing here has been confirmed on the owner's phone yet.** The [Phase 0 checklist](../phase-0/hardware-verification-checklist.md) confirms what can be confirmed without writing to the device. The checklist step for each fact is in the [summary table](#assumptions-requiring-physical-confirmation).

| **Fork** | Stated in the out-of-tree community mainline Linux fork [msm8227-mainline/linux](https://github.com/msm8227-mainline/linux) (branch `msm8227-6.19`). This is source code, but upstream Linux has not reviewed it. |

## Processor and architecture

- **ISA: ARMv7-A, 32-bit only.** There is no AArch64 execution state. Revival OS's first port is therefore `arch/arm32` ([ARCHITECTURE.md](../../ARCHITECTURE.md#portability)). (Source: LineageOS, postmarketOS)
- **Krait** is Qualcomm's own ARMv7-A implementation, not an Arm Cortex core. Its CPU nodes are `compatible = "qcom,krait"` with `enable-method = "qcom,kpss-acc-v1"`: the second core is started through Qualcomm's KPSS power controller, not PSCI. (Fork)
- **Floating point and SIMD:** the downstream kernel enables `CONFIG_VFP`, `CONFIG_NEON` and `CONFIG_KERNEL_MODE_NEON` (Source: [kernel defconfig](https://github.com/LineageOS/android_kernel_samsung_msm8930-common/blob/lineage-18.1/arch/arm/configs/samsung_serrano_defconfig)). The exact VFP version and hardware integer-divide support are **Unknown**. Checklist C5 records the `Features` line of `/proc/cpuinfo`.
- **Virtualization extensions (HYP mode):** **Unknown.** This affects which CPU mode the bootloader may hand over in (see [handoff](#boot-image-format-and-handoff)).
- **SoC family:** MSM8930 belongs to Qualcomm's MSM8960 family. LineageOS builds it as `TARGET_BOARD_PLATFORM := msm8960` and `TARGET_BOOTLOADER_BOARD_NAME := MSM8960` (Source).

## Boot chain

What is known, and how well:

```text
power on
  → Qualcomm primary boot loader (PBL, in SoC ROM)         Inference (MSM8960 family)
  → secondary boot loaders (expected: SBL1, SBL2, SBL3)    Community — confirm names with the PIT (F5)
  → TrustZone (TZ) and RPM firmware                        Community — confirm with the PIT (F5)
  → Samsung bootloader, "aboot" (based on Qualcomm's LK)   Inference
       ├─ key combination Vol Down + Home + Power → Download mode (Odin protocol)
       ├─ key combination Vol Up + Home + Power   → loads the `recovery` partition
       └─ otherwise                                → loads the `boot` partition
  → Linux kernel + Android (today)                         Source
```

Key points:

- **There is no BIOS, UEFI or fastboot on the stock chain.** lk2nd describes Samsung's flashing interface as "the proprietary flashing interface on Samsung devices" (Source: [lk2nd README](https://github.com/msm8916-mainline/lk2nd/blob/main/README.md)). LineageOS records `no_oem_unlock_switch: true` (Source).
- **The stock bootloader loads standard Android boot images**, and it runs non-Linux code from them. lk2nd is itself a non-Linux program "packed into an Android boot image, which is then loaded by the stock bootloader just like the original Android image", and it supports the GT-I9195 (Source: lk2nd README and [devices list](https://github.com/msm8916-mainline/lk2nd/blob/main/Documentation/devices.md)). This is the strongest public evidence that a custom bare-metal payload can be started on this phone (Inference). It is **not** evidence that Goose-generated code will run.
- **Qualcomm secure boot** is expected to be enabled on retail Samsung units. The signed early stages cannot be replaced (Community). Checklist F2 reads the Download-mode screen for a `QUALCOMM SECUREBOOT` line.
- **Download mode lives in the bootloader**, so it does not depend on the contents of `boot`, `recovery` or `system` (Inference, consistent with community recovery practice). This makes it the main recovery anchor, as long as the bootloader-chain partitions are never written.

## Boot image format and handoff

Boot-image parameters agree between [LineageOS](https://github.com/LineageOS/android_device_samsung_serrano-common/blob/lineage-18.1/BoardConfigCommon.mk) and [postmarketOS](https://gitlab.nura.eco/nura/pmaports/-/blob/main/device/archived/device-samsung-serranolte/deviceinfo) (Source):

| Parameter | Value |
| --- | --- |
| Format | Android boot image (`ANDROID!` header; header version 0, Inference from the kernel-3.4 era tooling) |
| Base | `0x80200000` |
| Kernel offset / load address | `0x00008000` → `0x80208000` |
| Ramdisk offset / address | `0x02000000` → `0x82200000` |
| Second-stage offset | `0x00f00000` |
| Tags offset / address | `0x00000100` → `0x80200100` |
| Page size | 2048 |
| Kernel format | `zImage` |
| Stock command line (LineageOS) | `androidboot.hardware=qcom user_debug=22 msm_rtb.filter=0x3F ehci-hcd.park=3 androidboot.bootdevice=msm_sdcc.1` |
| Maximum image size | 10 MiB (partition size) |
| Heimdall partition name | `BOOT` (postmarketOS `deviceinfo_flash_heimdall_partition_kernel="BOOT"`) |

**Board files, not a device tree.** The downstream kernel selects `CONFIG_MACH_SERRANO_EUR_LTE=y` for this variant ([defconfig](https://github.com/LineageOS/android_kernel_samsung_msm8930-common/blob/lineage-18.1/arch/arm/configs/msm8930_serrano_eur_lte_defconfig)), and the kernel's [`mach-types`](https://github.com/LineageOS/android_kernel_samsung_msm8930-common/blob/lineage-18.1/arch/arm/tools/mach-types) lists `serrano` with machine number 3727 (Source). So the stock bootloader most likely passes an ATAGS list, not a device tree (Inference). Whether it can pass a DTB is **Unknown**.

**Entry state.** The ARM Linux boot protocol requires `r0 = 0`, `r1` = machine type, `r2` = physical address of the ATAGS list or DTB, all interrupts disabled, MMU off, data cache off, and SVC mode (or HYP mode on CPUs with virtualization extensions) ([Linux: Booting ARM Linux](https://docs.kernel.org/arch/arm/booting.html), Source). The stock bootloader boots Linux, so it presumably meets this (Inference). The **actual** values are measured in Phase 2 and written into the boot handoff contract.

**Samsung-specific image checks** (signature warnings, footers) for this bootloader version: **Unknown**. They are observed during Phase 2.

## Bootloader lock and Knox

- **No unlock step is documented for the GT-I9195.** LineageOS records no OEM-unlock switch. TWRP's official page offers an "Odin Install Method (No Root Required)", and postmarketOS flashes with Heimdall (Source: [TWRP](https://twrp.me/samsung/samsunggalaxys4minilte.html), postmarketOS deviceinfo). So the international variant's bootloader accepts unsigned `boot` and `recovery` images (Inference).
- **Knox warranty bit.** Community reports say that on Samsung devices with a Knox-enabled bootloader, flashing a non-Samsung kernel or recovery permanently sets `KNOX WARRANTY VOID: 0x1`, described as a hardware eFuse ([Chainfire](https://chainfire.eu/articles/796/More_on_KNOX_warranty_void); forum reports). Whether this unit's bootloader has Knox depends on its firmware version (Community). **Treat any non-Samsung write as irreversibly marking the device.** On a 2013 phone the practical cost is the Knox features, not a warranty, but the owner must accept it explicitly before Phase 2. Checklist F2 records the current value.
- **Reactivation lock** (Samsung account) may block flashing when enabled (Community). Checklist F2 records it.
- **Downgrades.** The bootloader may refuse firmware older than itself (Community). The restore source must therefore match the **installed** build (checklist G1–G3).

## Recovery mechanisms

From most to least independent of what has been written:

| # | Mechanism | Depends on | How to use | Confidence |
| --- | --- | --- | --- | --- |
| 1 | Remove the battery | Nothing | Removing the battery ends any hang, loop or stuck mode | Source (removable battery) |
| 2 | Download mode | Bootloader chain only | Vol Down + Home + Power from power-off; flash stock images with Heimdall | Source (key combination); Inference (independence) |
| 3 | Reflash stock `boot` / `recovery` | Download mode, Heimdall, verified stock images for the installed build | `heimdall flash --BOOT boot.img` (or `--RECOVERY`) from Download mode | Source (Heimdall); the stock images must still be obtained (G2) |
| 4 | Full stock firmware flash | Download mode, complete matching firmware | Restores `system`, `boot`, `recovery`, modem. It **also rewrites bootloader images**, so it is a last resort and only with the exact installed build. | Community |
| 5 | Stock recovery | `recovery` partition intact | Vol Up + Home + Power; only "reboot system now" is used | Source (key combination) |
| 6 | Qualcomm emergency download (EDL) | SoC ROM; a Samsung-signed programmer, which is not publicly available | Not a usable plan | Community / Unknown |
| 7 | SD-card or JTAG/eMMC-direct "debrick" | Specialist images or hardware | Not a usable plan | Community / Unknown |

**Download mode cannot read partitions back.** Heimdall reads only the PIT (partition table) from the device (Community, consistent with the [Heimdall manual](https://manpages.debian.org/bookworm/heimdall-flash/heimdall.1), which documents `print-pit`/`download-pit` and flashing only). Without root or a custom recovery there is **no raw backup** of `boot`, `recovery`, `efs` or `persist`. The restore source for `boot` and `recovery` is therefore the matching stock firmware package (G2). `efs` and `persist` are protected by never writing them.

## Debug output interfaces

Ranked by how early they could serve Revival OS:

1. **Bootloader framebuffer (best Phase 2 candidate).** The mainline fork describes a `simple-framebuffer` at `0x88300000`, 540×960, 24-bit `r8g8b8`, stride 1620 bytes (Fork). A `simple-framebuffer` means the display was left running by earlier boot code (Inference). It is **Unknown** whether the *stock* bootloader leaves it active when it boots the `recovery` partition, or whether the fork relies on lk2nd. Phase 2 tests this directly: a solid colour written there should appear.
2. **UART through the micro-USB port.** The console UART is GSBI5's UART-DM at `0x16440000`, `115200n8` (Fork). The phone's TSU6721 micro-USB switch driver defines `ADC_JIG_UART_ON` (`0x1d`) and `ADC_JIG_UART_OFF` (`0x1c`) modes and a UART switch path (Source: [tsu6721.c](https://github.com/LineageOS/android_kernel_samsung_msm8930-common/blob/lineage-18.1/drivers/misc/tsu6721.c)). On other Samsung models, a 619 kΩ resistor between the micro-USB ID pin and ground selects the UART, at 1.8 V and 115200 8N1 (Community: [Replicant UART notes](https://redmine.replicant.us/projects/replicant/wiki/UART), [postmarketOS serial debugging](https://wiki.postmarketos.org/wiki/Serial_debugging)). For the GT-I9195, the resistor value, voltage, routing and whether the bootloader prints anything are **Unknown**. This needs a 1.8 V-capable USB-UART adapter and a micro-USB breakout that exposes the ID pin. **A wrong voltage can damage the phone.** It is not part of Phase 0.
3. **The reset itself.** A payload that resets the device after a fixed delay gives a one-bit observable result with no display or cable (Inference). The reset mechanism (PS_HOLD, watchdog) is still to be researched.
4. **Persistent RAM log.** The downstream kernel enables `CONFIG_ANDROID_RAM_CONSOLE=y` (Source), a RAM region that survives a warm reset. Its address is **Unknown**. It is a candidate for Phase 3e crash records.
5. **Vibrator and LEDs.** These need PMIC programming. The fork notes the vibrator is driven through regulator `l33` (Fork). They are not early options.

## Camera hardware

- Rear 8 MP with LED flash; front 1.9 MP (Source: LineageOS).
- LineageOS ships camera tuning libraries for **two** rear sensors, Sony **IMX175** and Samsung **S5K3H5XA**, and one front sensor, Samsung **S5K6A3YX** (Source: [proprietary-files.txt](https://github.com/LineageOS/android_device_samsung_serrano-common/blob/lineage-18.1/proprietary-files.txt)). Units were probably built with either rear sensor (Inference). **Which one this phone has is Unknown** (checklist C6).
- Pipeline: the downstream kernel's Qualcomm camera stack (MIPI CSI, CSID, VFE; `board-8930-camera.c` in the [kernel](https://github.com/LineageOS/android_kernel_samsung_msm8930-common/tree/lineage-18.1/arch/arm/mach-msm)) plus a proprietary user-space daemon (`mm-qcamera-daemon`) and per-sensor "chromatix" tuning libraries (Source: proprietary-files.txt).
- Video codec firmware: `vidc_1080p.fw`, `vidcfw.elf` (Source: proprietary-files.txt).
- **Implication for Phase 6:** Revival OS must drive the sensor over its control bus, program the CSI receiver and VFE, sequence the clocks and regulators, and do without the proprietary ISP tuning, which is Android user-space code. Raw sensor frames are the realistic first target. Hardware video encoding needs vendor firmware. This is the project's highest-risk area.

## Wi-Fi hardware

- 802.11 a/b/g/n (Source: LineageOS).
- Qualcomm's WCNSS integrated Wi-Fi/Bluetooth core, driven on Android by the `prima` driver (`wlan.ko`, `BOARD_WLAN_DEVICE := qcwcn`, `CONFIG_PRIMA_WLAN=m`, `CONFIG_WCNSS_CORE=y`) (Source: [msm8930-common BoardConfigCommon.mk](https://github.com/LineageOS/android_device_samsung_msm8930-common/blob/lineage-18.1/BoardConfigCommon.mk), kernel defconfig).
- Configuration and calibration files `WCNSS_qcom_cfg.ini` and `WCNSS_qcom_wlan_nv.bin` (Source: serrano-common `prima/`). Reserved WCNSS memory at `0x8f000000` (Fork).
- The WCNSS firmware image is probably stored in the `modem` partition (mounted at `/firmware`) and loaded by the application CPU with TrustZone authentication (Inference from MSM8960-family Linux support). The RF companion chip is **Unknown**.
- postmarketOS publishes a `firmware-samsung-serranolte-wlan` package (Source: [pkgs.postmarketos.org](https://pkgs.postmarketos.org/package/main/postmarketos/armv7/firmware-samsung-serranolte-wlan)).
- **Implication for Phase 5:** Wi-Fi needs vendor firmware loading through TrustZone, the WCNSS host interface, and calibration data. USB networking is an alternative route, to be weighed in review.

## Proprietary firmware and driver limitations

| Area | Limitation |
| --- | --- |
| Early boot (PBL, SBLs, TZ, RPM, aboot) | Signed vendor code. It cannot be replaced and stays under Revival OS. |
| TrustZone | Some operations (peripheral firmware authentication, possibly secondary-core start) need secure-monitor calls with undocumented interfaces (Inference). |
| RPM | Many regulators and shared clocks are owned by the RPM firmware and are requested through a message protocol (Fork: `rpm` regulators node). |
| Wi-Fi / Bluetooth | Vendor WCNSS firmware and calibration NV data. |
| Modem | Vendor firmware. Not used by Revival OS. |
| Camera ISP tuning | Proprietary Android user-space libraries. Not usable. |
| Video codec, GPU | Vendor firmware and microcode (`vidc_1080p.fw`, `a300_pfp.fw`, `a300_pm4.fw`). |
| Documentation | No public Qualcomm register documentation for MSM8930. Driver knowledge comes from GPL kernel source and community mainline work. |
| Redistribution | Vendor firmware and Samsung firmware packages are **never committed** to Revival repositories. Revival OS reads firmware from the phone's own partitions. |

| Losing `efs` or `persist` (radio identity, calibration) | Permanent loss of identity and calibration | Never written. No tool or plan touches them. |
| Knox warranty bit set by the first non-Samsung image | Irreversible marking | Owner's explicit acceptance before Phase 2 |
| Flashing an image for the wrong variant | Unbootable device | Model confirmed twice (B1, C5); image checks name the device |
| No matching stock firmware for restore | `boot`/`recovery` cannot be restored | Phase 2 is blocked until G1–G3 pass |
| Power loss during a flash | Corrupt partition | Battery checked and charged (B2, B3); good cable; no flashing on a weak battery |
| Old, swollen or failing battery | Fire risk, unstable power | B2 inspection; stop if swollen |
| Wrong voltage on a UART cable | Hardware damage | UART deferred; 1.8 V adapter verified before use |
| Erasing Android loses the hardware reference | No known-good comparison for camera, Wi-Fi and display behaviour | Android kept until at least Phase 7 |
| Driver mis-programming regulators or the PMIC | Hardware damage | Only documented voltage ranges; RPM requests preferred |
| Operating Wi-Fi outside regulatory limits | Legal and interference risk | Device calibration and country configuration honoured (Phase 5) |
| Owner's personal data on the phone | Data loss | D1 backup, decided by the owner |

## Recoverability after failed boot experiments

Assuming Phase 0 has verified Download mode and the stock images, and nothing outside the approved partition is written:

| Failure | Expected state | Recovery | Confidence |
| --- | --- | --- | --- |
| Test image in `recovery` does nothing, hangs or loops | Stuck or looping in the test image | Remove the battery; normal power-on boots Android from the untouched `boot` | High (Inference: separate partitions, separate key paths) |
| Test image in `boot` hangs or loops | Android does not start | Remove the battery; Download mode; reflash stock `boot.img` | High, if stock `boot.img` matches the installed build |
| Bootloader rejects the image | Error screen or Download mode | Reflash the stock image to that partition | Medium (behaviour **Unknown** until observed) |
| Watchdog resets the device repeatedly | Reboot loop | Remove the battery; Download mode; restore | High |
| Payload writes storage by mistake (later phases) | Possible damage to `system`/`userdata`, or worse | Full stock flash; `efs`/`persist` damage may be permanent | Low. Prevented by keeping eMMC read-only until Phase 4 review. |
| Bootloader chain damaged | No Download mode | None practical | Not recoverable: prevented by never writing it |
